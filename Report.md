# Итоговый отчет по аудиту конфигурации

## Область проверки

Проверены `docker-compose.yml`, Dockerfile всех сервисов, конфигурация nginx, оба Flask-приложения, общий HTML-шаблон, SSL-сертификат и README. После исправлений выполнена фактическая проверка Docker Compose в PowerShell на Windows.

## Найденные проблемы и исправления

| Уровень | Проблема | Исправление |
|---|---|---|
| Критический | SSL-сертификат был просрочен: срок действия заканчивался 15 августа 2023 года. | Выпущен новый самоподписанный сертификат RSA/SHA-256 с SAN для `localhost`, `www.example.com` и `127.0.0.1`. Сертификат предназначен для локальной разработки, поэтому браузер может потребовать подтверждение доверия. |
| Критический | Dockerfile nginx не копировал сертификат и приватный ключ в образ, поэтому nginx не мог запустить SSL. | Добавлено копирование файлов в `/etc/nginx/certs`; в `nginx.conf` используются абсолютные пути. |
| Критический | `proxy_pass` ссылался на несуществующий upstream `app`. | Использован объявленный upstream `loadbalancer`. |
| Высокий | nginx направлял запросы на порт 81, тогда как приложения слушали 8080 и 80. | Оба приложения унифицированы на внутреннем порту 8080; upstream настроен на `app1:8080` и `app2:8080`. |
| Высокий | Публиковалась связка `445:445`, хотя nginx слушает 443 и README описывает `https://localhost`. | Порт изменен на `443:443`. |
| Высокий | `app2/Dockerfile` запускал `app1.py`, отсутствующий в контексте `app2`. | Исправлено на `CMD ["app2.py"]`. После пересборки контейнер запускается командой `python3 app2.py`. |
| Высокий | Из-за остановленного `app2` nginx не мог разрешить upstream `app2:8080` и завершался с ошибкой `host not found in upstream`. | После исправления `app2` выполнены пересборка и пересоздание контейнеров; nginx успешно разрешает оба backend. |
| Высокий | Для демонстрации последовательного round-robin nginx использовал много worker-процессов (`worker_processes auto`). | Для учебной демонстрации задан один worker-процесс, что обеспечивает наблюдаемое чередование `app1` и `app2`. |
| Высокий | Flask искал шаблон в стандартном каталоге `templates`, но шаблон монтировался в `/storage`. | Flask явно использует `template_folder='/storage'`; volume оставлен read-only. |
| Средний | Корневой URL `/` из README не обслуживался: был только маршрут `/hello`. | Добавлены маршруты `/` и `/hello` в оба приложения. |
| Средний | Приложение app2 не передавало `source_app`, поэтому шаблон не показывал источник ответа. | В app2 передается `source_app='app2'`. |
| Средний | `debug=True` включал отладчик Flask и небезопасен для контейнера, доступного через reverse proxy. | Отладка отключена (`debug=False`). |
| Средний | `least_conn` не соответствует требованию демонстрационной последовательной балансировки. | Убран параметр `least_conn`; используется стандартный round-robin nginx. |
| Средний | Разрешались устаревшие TLSv1 и TLSv1.1. | Оставлены TLSv1.2 и TLSv1.3. |
| Низкий | В HTML был ошибочный закрывающий тег `</h1>` без открывающего тега. | Исправлено на корректную пару `<h1>...</h1>`. |
| Низкий | В Dockerfile использовался pip без отключения кэша. | Добавлен `--no-cache-dir`, чтобы уменьшить размер образов. |

## Дополнительные изменения конфигурации

- Устаревший ключ `version` удален из Compose-файла.
- В Compose добавлены `expose: 8080` для явного описания внутреннего API backend-сервисов без публикации их наружу.
- В nginx добавлены заголовки `Host`, `X-Forwarded-For` и `X-Forwarded-Proto`.
- В Dockerfile приложений добавлены `WORKDIR /app`, `EXPOSE 8080` и установка зависимостей без кэша.
- Образы приложений работают от непривилегированного пользователя `www`.

## Runtime-проверка

Выполнены команды:

```powershell
docker compose config
docker compose up -d --force-recreate
docker compose ps -a
docker compose exec nginx nginx -t
```

Фактическое состояние контейнеров после исправления:

```text
app1   Up
app2   Up
nginx  Up    0.0.0.0:443->443/tcp
```

Подтверждено, что оба имени разрешаются внутри сети Compose:

```text
172.18.0.2 app1
172.18.0.3 app2
```

Прямые запросы из nginx к обоим приложениям завершились с `HTTP/1.1 200 OK`:

```text
http://app1:8080/hello -> Hello World from app1!
http://app2:8080/hello -> Hello World from app2!
```

HTTPS-проверки с хоста также завершились успешно:

```powershell
curl.exe -k -i https://localhost/
curl.exe -k -i https://localhost/hello
```

Оба адреса вернули `HTTP/1.1 200 OK`. При последовательных запросах диагностический заголовок подтвердил round-robin:

```text
172.18.0.2:8080 -> app1
172.18.0.3:8080 -> app2
172.18.0.2:8080 -> app1
172.18.0.3:8080 -> app2
```

## Итог

Runtime-проблема устранена. `app2` больше не завершается с ошибкой отсутствующего `app1.py`, nginx успешно запускается и разрешает оба upstream. HTTPS на `https://localhost/` и `https://localhost/hello` работает, а запросы распределяются между `app1` и `app2` по round-robin.
